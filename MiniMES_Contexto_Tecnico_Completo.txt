3. PRINCÍPIOS DE DESENVOLVIMENTO
================================

3.1 Desenvolvimento incremental
-------------------------------

Não implementar dezenas de arquivos ou vários microsserviços de uma só vez.

Cada etapa deve:

1. explicar o objetivo;
2. apresentar os arquivos envolvidos;
3. fornecer o código;
4. explicar a sintaxe específica de C#;
5. explicar a conexão entre as camadas;
6. compilar;
7. testar;
8. manter o projeto funcionando.

3.2 Evitar overengineering
--------------------------

Não criar abstrações apenas por aparência arquitetural.

Exemplos a evitar:

- GenericRepository<T> que apenas replica Add, Remove e Find do DbSet;
- interfaces sem uma razão real;
- dezenas de microsserviços desde o primeiro commit;
- padrões complexos antes de existir uma regra de negócio;
- múltiplos bancos antes da extração real de serviços;
- eventos para operações puramente locais e simples.

3.3 Controller fino
-------------------

O controller deve cuidar apenas de:

- HTTP;
- rotas;
- parâmetros;
- autenticação e autorização;
- contratos de entrada;
- contratos de saída;
- status HTTP.

O controller não deve:

- executar consultas do EF Core;
- conter regras de domínio;
- chamar SaveChanges diretamente;
- decidir transações;
- alterar entidades arbitrariamente.

3.4 Regras dentro do domínio
----------------------------

Estados importantes não devem ter setters públicos.

Evitar:

order.Status = ProductionOrderStatus.Completed;

Preferir:

order.Complete();

A entidade deve validar se a transição é permitida.

3.5 Um SaveChanges sempre que possível
--------------------------------------

Sempre que possível:

- carregar entidades;
- aplicar regras;
- adicionar todas as alterações;
- chamar SaveChangesAsync uma única vez.

Isso permite utilizar a transação automática do Entity Framework Core.

5. ESTRATÉGIA ARQUITETURAL
==========================

5.1 Arquitetura inicial
-----------------------

O projeto deve começar como um monólito modular.

Cliente HTTP ou React
        ↓
ASP.NET Core Web API
        ↓
Controllers
        ↓
Application Services
        ↓
Repositories
        ↓
Entity Framework Core
        ↓
PostgreSQL

5.2 Fluxo interno principal
---------------------------

Controller
    ↓
IService
    ↓
Service
    ↓
IRepository
    ↓
Repository
    ↓
DbContext
    ↓
PostgreSQL

5.3 Responsabilidades
---------------------

Controller:

- recebe request;
- valida entrada HTTP;
- transforma request em command;
- chama service;
- transforma resultado em response;
- retorna status HTTP.

Service:

- representa o caso de uso;
- coordena repositories;
- chama métodos das entidades;
- executa regras de aplicação;
- decide quando salvar;
- decide quando iniciar transação explícita;
- retorna DTOs.

Repository:

- contém consultas do Entity Framework Core;
- decide tracking ou AsNoTracking;
- usa Include quando necessário;
- adiciona e remove entidades;
- abstrai consultas específicas do domínio;
- não deve controlar o caso de uso inteiro.

Unit of Work:

- executa SaveChangesAsync;
- confirma alterações feitas por diferentes repositories;
- pode expor controle de transação explícita;
- compartilha o mesmo DbContext dos repositories.

DbContext:

- representa uma sessão de trabalho com o banco;
- faz tracking das entidades;
- traduz LINQ em SQL;
- executa SaveChanges;
- configura o provider PostgreSQL.

Entidade:

- protege seu estado;
- valida invariantes;
- controla transições;
- não depende de ASP.NET Core;
- idealmente não depende de EF Core diretamente.

7. CONFIGURAÇÃO DO POSTGRESQL
=============================

O PostgreSQL deve ser executado localmente por Docker Compose.

Exemplo de compose.yaml:

services:
  postgres:
    image: postgres:18-alpine
    container_name: minimes-postgres

    environment:
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}

    ports:
      - "${POSTGRES_PORT}:5432"

    volumes:
      - minimes_postgres_data:/var/lib/postgresql

    healthcheck:
      test:
        [
          "CMD-SHELL",
          "pg_isready -U ${POSTGRES_USER} -d ${POSTGRES_DB}"
        ]
      interval: 5s
      timeout: 5s
      retries: 10

    restart: unless-stopped

volumes:
  minimes_postgres_data:

Exemplo de .env local:

POSTGRES_DB=minimes
POSTGRES_USER=minimes
POSTGRES_PASSWORD=<senha-local>
POSTGRES_PORT=5432

O arquivo .env não deve ser versionado.

Comandos úteis:

docker compose up -d
docker compose ps
docker compose logs postgres
docker compose stop
docker compose start
docker compose down
docker compose down -v

A opção -v remove o volume e apaga os dados locais.

Teste de disponibilidade:

docker compose exec postgres \
  pg_isready -U minimes -d minimes

Abrir psql:

docker compose exec postgres \
  psql -U minimes -d minimes


8. CONNECTION STRING
====================

A connection string não deve ficar com senha diretamente no Git.

Em desenvolvimento, usar user secrets:

dotnet user-secrets init

dotnet user-secrets set \
  "ConnectionStrings:Postgres" \
  "Host=localhost;Port=5432;Database=minimes;Username=minimes;Password=<senha>"

Leitura no Program.cs:

string connectionString =
    builder.Configuration.GetConnectionString("Postgres")
    ?? throw new InvalidOperationException(
        "A connection string 'Postgres' não foi configurada."
    );

O operador ?? utiliza o valor da esquerda e, se ele for null, utiliza o valor da
direita. Neste caso, lança uma exceção clara durante a inicialização.

9.1 DbContext
-------------

O DbContext deve permanecer pequeno.

Exemplo:

using Microsoft.EntityFrameworkCore;
using MiniMes.Api.Domain.Entities;

namespace MiniMes.Api.Data;

public sealed class MiniMesDbContext : DbContext
{
    public MiniMesDbContext(
        DbContextOptions<MiniMesDbContext> options
    ) : base(options)
    {
    }

    public DbSet<Product> Products =>
        Set<Product>();

    public DbSet<ProductionOrder> ProductionOrders =>
        Set<ProductionOrder>();

    public DbSet<ProductionOperation> ProductionOperations =>
        Set<ProductionOperation>();

    public DbSet<OperationExecution> OperationExecutions =>
        Set<OperationExecution>();

    public DbSet<ProductionReport> ProductionReports =>
        Set<ProductionReport>();

    protected override void OnModelCreating(
        ModelBuilder modelBuilder
    )
    {
        base.OnModelCreating(modelBuilder);

        modelBuilder.ApplyConfigurationsFromAssembly(
            typeof(MiniMesDbContext).Assembly
        );
    }
}

9.2 Configuração por entidade
-----------------------------

Cada entidade deve ter uma classe própria:

public sealed class ProductionOrderConfiguration
    : IEntityTypeConfiguration<ProductionOrder>
{
    public void Configure(
        EntityTypeBuilder<ProductionOrder> builder
    )
    {
        // mapeamento
    }
}

ApplyConfigurationsFromAssembly procura automaticamente classes que implementam:

IEntityTypeConfiguration<T>

9.3 Tracking
------------

Para consultas somente leitura:

.AsNoTracking()

Para entidades que serão alteradas:

- não utilizar AsNoTracking;
- carregar a entidade com tracking;
- alterar pela entidade;
- chamar SaveChangesAsync.

9.4 IQueryable
--------------

Consultas EF Core normalmente constroem um IQueryable.

A consulta só é executada quando ocorre uma operação terminal, por exemplo:

- ToListAsync;
- FirstOrDefaultAsync;
- SingleAsync;
- CountAsync;
- AnyAsync.

9.5 Migrations
--------------

Criar migration quando houver alteração no esquema:

- nova tabela;
- nova coluna;
- alteração de tipo;
- índice;
- chave estrangeira;
- restrição.

Mover classes de pasta ou namespace, mantendo o mesmo mapeamento, não deveria gerar
alteração de esquema.

Não editar migration antiga que já foi aplicada em ambientes compartilhados.
Criar uma nova migration.


10. INJEÇÃO DE DEPENDÊNCIA
==========================

Não é o C# que injeta automaticamente dependências.

Quem faz isso é o container de DI do ASP.NET Core.

O campo privado apenas armazena a dependência:

private readonly IProductionOrderRepository _repository;

A dependência é declarada no construtor:

public ProductionOrderService(
    IProductionOrderRepository repository
)
{
    _repository = repository;
}

O registro acontece no Program.cs:

builder.Services.AddScoped<
    IProductionOrderRepository,
    ProductionOrderRepository
>();

builder.Services.AddScoped<
    IProductionOrderService,
    ProductionOrderService
>();

10.1 Ciclos de vida
-------------------

Scoped:

- uma instância por escopo;
- em API web, normalmente uma instância por requisição;
- recomendado para DbContext, repositories e services relacionados.

Transient:

- uma nova instância cada vez que o serviço é solicitado;
- adequado para objetos leves e sem estado compartilhado.

Singleton:

- uma instância para toda a aplicação;
- não deve depender diretamente de DbContext scoped;
- exige cuidado com thread safety.

O DbContext é registrado como Scoped por padrão pelo AddDbContext.


11. UNIT OF WORK E TRANSAÇÕES
=============================

11.1 Transação automática
-------------------------

Cada SaveChangesAsync é transacional quando o provider suporta transações.

Exemplo:

_orderRepository.Add(order);
_historyRepository.Add(history);

await _unitOfWork.SaveChangesAsync(cancellationToken);

Se os dois repositories compartilham o mesmo DbContext, os dois inserts podem ser
confirmados na mesma transação.

11.2 Interface da Unit of Work
------------------------------

public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(
        CancellationToken cancellationToken
    );
}

Implementação:

public sealed class UnitOfWork : IUnitOfWork
{
    private readonly MiniMesDbContext _dbContext;

    public UnitOfWork(
        MiniMesDbContext dbContext
    )
    {
        _dbContext = dbContext;
    }

    public Task<int> SaveChangesAsync(
        CancellationToken cancellationToken
    )
    {
        return _dbContext.SaveChangesAsync(
            cancellationToken
        );
    }
}

11.3 Transação explícita
------------------------

Usar transação explícita quando:

- existem vários SaveChangesAsync;
- todos precisam ser atômicos;
- existem comandos EF Core e SQL manual;
- há vários passos de banco que não podem ser reunidos em um SaveChanges.

Não abrir transação explícita para toda operação simples.

Não manter transação aberta durante:

- chamada HTTP externa;
- publicação em broker;
- espera de usuário;
- processamento demorado.

11.4 Banco e NATS
-----------------

Uma transação PostgreSQL não inclui automaticamente uma publicação no NATS.

Para banco + mensageria, utilizar Transactional Outbox:

1. alterar entidade;
2. gravar mensagem na outbox;
3. chamar SaveChangesAsync;
4. worker lê outbox;
5. worker publica no NATS;
6. marca mensagem como processada.


12. REPOSITORIES
================

Não criar repository genérico apenas para envolver o DbSet.

Interface de exemplo:

public interface IProductionOrderRepository
{
    Task<IReadOnlyList<ProductionOrder>> GetAllAsync(
        CancellationToken cancellationToken
    );

    Task<ProductionOrder?> GetByIdAsync(
        Guid id,
        CancellationToken cancellationToken
    );

    Task<ProductionOrder?> GetByIdForUpdateAsync(
        Guid id,
        CancellationToken cancellationToken
    );

    void Add(ProductionOrder productionOrder);
}

Consulta somente leitura:

public async Task<IReadOnlyList<ProductionOrder>> GetAllAsync(
    CancellationToken cancellationToken
)
{
    return await _dbContext
        .ProductionOrders
        .AsNoTracking()
        .OrderByDescending(order => order.CreatedAt)
        .ToListAsync(cancellationToken);
}

Consulta para alteração:

public Task<ProductionOrder?> GetByIdForUpdateAsync(
    Guid id,
    CancellationToken cancellationToken
)
{
    return _dbContext
        .ProductionOrders
        .Include(order => order.Operations)
        .FirstOrDefaultAsync(
            order => order.Id == id,
            cancellationToken
        );
}

Não usar AsNoTracking em uma entidade que será alterada pelo mesmo DbContext.


13. SERVICES
============

O service representa o caso de uso.

Exemplo de interface:

public interface IProductionOrderService
{
    Task<IReadOnlyList<ProductionOrderDto>> GetAllAsync(
        CancellationToken cancellationToken
    );

    Task<ProductionOrderDto?> GetByIdAsync(
        Guid id,
        CancellationToken cancellationToken
    );

    Task<ProductionOrderDto> CreateAsync(
        CreateProductionOrderCommand command,
        CancellationToken cancellationToken
    );

    Task ReleaseAsync(
        Guid id,
        CancellationToken cancellationToken
    );
}

Exemplo de criação:

public async Task<ProductionOrderDto> CreateAsync(
    CreateProductionOrderCommand command,
    CancellationToken cancellationToken
)
{
    Product? product =
        await _productRepository.GetByIdAsync(
            command.ProductId,
            cancellationToken
        );

    if (product is null)
    {
        throw new ProductNotFoundException(
            command.ProductId
        );
    }

    if (!product.IsActive)
    {
        throw new InactiveProductException(
            command.ProductId
        );
    }

    var order = new ProductionOrder(
        command.OrderNumber,
        command.ProductId,
        command.PlannedQuantity,
        command.Priority
    );

    _productionOrderRepository.Add(order);

    await _unitOfWork.SaveChangesAsync(
        cancellationToken
    );

    return ProductionOrderDto.FromEntity(order);
}

Exemplo de liberação:

public async Task ReleaseAsync(
    Guid id,
    CancellationToken cancellationToken
)
{
    ProductionOrder? order =
        await _productionOrderRepository
            .GetByIdForUpdateAsync(
                id,
                cancellationToken
            );

    if (order is null)
    {
        throw new ProductionOrderNotFoundException(id);
    }

    order.Release();

    await _unitOfWork.SaveChangesAsync(
        cancellationToken
    );
}


14. REQUESTS, COMMANDS E DTOS
============================

Não passar diretamente o request HTTP ao service.

Fluxo:

CreateProductionOrderRequest
        ↓
CreateProductionOrderCommand
        ↓
ProductionOrderService
        ↓
ProductionOrder
        ↓
ProductionOrderDto

Request:

- pertence à API;
- representa JSON;
- pode usar DataAnnotations;
- não deve ser usado como entidade.

Command:

- pertence à camada Application;
- representa intenção de negócio;
- pode ser um record.

DTO:

- representa saída da aplicação;
- evita retornar entidade diretamente;
- protege o contrato público da API.

Exemplo:

public sealed record CreateProductionOrderCommand(
    string OrderNumber,
    Guid ProductId,
    decimal PlannedQuantity,
    int Priority
);

public sealed record ProductionOrderDto(
    Guid Id,
    string OrderNumber,
    Guid ProductId,
    decimal PlannedQuantity,
    string Status,
    int Priority,
    DateTime CreatedAt
);

====================

16.1 Product
------------

16.2 ProductionOrder
--------------------

Campos:

- Id;
- OrderNumber;
- ProductId;
- PlannedQuantity;
- Status;
- Priority;
- PlannedStartAt;
- PlannedEndAt;
- CreatedAt;
- ReleasedAt;
- Version;
- Operations.

Status:

public enum ProductionOrderStatus
{
    Draft = 1,
    Released = 2,
    InProgress = 3,
    Completed = 4,
    Cancelled = 5
}

Transições:

Draft → Released
Draft → Cancelled
Released → InProgress
Released → Cancelled
InProgress → Completed

Regras:

- quantidade planejada maior que zero;
- número da ordem único;
- deve possuir pelo menos uma operação antes da liberação;
- ordem cancelada não pode iniciar;
- ordem concluída não pode ser alterada;
- só pode concluir quando todas as operações estiverem concluídas.

Métodos:

- AddOperation;
- Release;
- Start;

20. CONCORRÊNCIA OTIMISTA
=========================

Entidades alteradas por vários terminais devem possuir um token de versão.

Exemplo:

public Guid Version { get; private set; }

Configuração:

builder
    .Property(entity => entity.Version)
    .HasColumnName("version")
    .IsConcurrencyToken();

Antes de salvar uma alteração, atualizar Version.

Quando ocorrer DbUpdateConcurrencyException:

- capturar no middleware ou camada apropriada;
- retornar HTTP 409 Conflict;
- informar que o recurso foi alterado por outro processo.

Cenários:

- dois operadores apontando produção;
- dois supervisores alterando a ordem;
- operação encerrada enquanto outro terminal envia apontamento.

24. TRANSACTIONAL OUTBOX
========================

Fluxo:

1. entidade gera evento;
2. service altera entidade;
3. service cria OutboxMessage;
4. SaveChangesAsync grava tudo;
5. OutboxPublisher.Worker consulta mensagens pendentes;
6. publica no NATS;
7. marca ProcessedAt;
8. registra tentativas e erros.

O evento e a alteração de negócio ficam na mesma transação PostgreSQL.
